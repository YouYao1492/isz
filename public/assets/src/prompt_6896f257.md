Project: Modern Electronics & Accessories Catalog Website

1. Project Overview

Build a modern, professional, mobile-first website for a physical retail shop selling electronics and accessories.

The website is an online product catalog, not a full e-commerce store. Customers should be able to browse products, search for items, compare specifications, check prices, inquire about availability, and visit the physical shop to purchase products in person.

The product catalog will contain approximately 100–500 products. Product information will be managed through Google Sheets so the shop owner can update the catalog without editing code.

Primary business goals
Showcase all products in an attractive and organized catalog.
Help customers quickly find products using search, categories, brands, and technical filters.
Display accurate product names, prices, photos, specifications, and compatibility information.
Encourage customers to visit the physical shop.
Let customers contact the shop to ask about product availability.
Make product maintenance simple through Google Sheets.
Important limitations
Do not implement online checkout.
Do not implement online payments.
Do not implement shipping or delivery management.
Do not require customer accounts.
Do not build a shopping cart in version one.
Do not invent real store details, inventory, product specifications, or prices.
Do not expose private Google Sheets credentials or sensitive business data in frontend code.

Use realistic sample data during development and clearly identify it as demonstration data.

2. Technology and Architecture

Use the following stack unless the existing project requires a compatible alternative:

Frontend: Next.js with TypeScript.
Styling: Tailwind CSS.
UI components: Accessible, reusable components.
Icons: Lucide icons.
Product data: Google Sheets.
Data access: Google Sheets API through a server-side endpoint, or a carefully restricted read-only published feed.
Hosting: Vercel or another compatible hosting platform.
Product images: Publicly accessible, stable image URLs or an appropriate image hosting service.
SEO: Server-rendered or statically generated product pages with unique metadata.

Keep the architecture simple and maintainable.

Use reusable components rather than creating a separate custom implementation for every product.

The website must work well on mobile phones, tablets, laptops, and desktop screens.

Do not put Google API keys, service-account credentials, or other private secrets into browser-delivered code.

Use environment variables for server-side credentials.

Implement sensible caching and revalidation so the website does not need to fetch the entire spreadsheet for every visitor request.

Document how the website retrieves and refreshes product data.

Data rules
SKU must uniquely identify each product.
Slugs must be unique and stable.
Prices must be valid numeric values.
Currency must be explicit and consistent with the shop's actual pricing.
Published products appear on the public website.
Unpublished products must not appear in public listings, search results, related products, or public API responses.
Missing optional fields must not break rendering.
Invalid rows must be logged and handled gracefully.
Product images must have fallbacks.
Technical specifications must be accurate and supplied by the shop or a trustworthy source.
Spreadsheet organization

Prefer a structured workbook with separate tabs when needed:

Products.
Categories.
Store Settings.

Avoid storing private costs, supplier contacts, or confidential notes in a publicly accessible data source.

Data access and security

For a private spreadsheet, access it using a server-side Google Sheets API integration.

For a public read-only feed, publish only a dedicated sheet containing fields safe for public access.

Never expose private credentials in client-side JavaScript.

Validate and normalize spreadsheet data before rendering it.

Use caching or revalidation rather than requesting the spreadsheet on every page interaction.

Document how to configure Google API credentials, spreadsheet ID, worksheet names, and refresh intervals.

Data refresh behavior

The website should refresh catalog data according to a documented interval or revalidation policy.

Do not promise instant updates unless the architecture actually supports them.

When a spreadsheet update is detected or the cache expires, the website should show the latest valid published information.
